Accessible states and exercise flow

The redesign should keep camera tracking and an exercise session as independent state dimensions. BlinkMore already models starting, calibrating, tracking, eyesClosed, noFace, multipleFaces, lowQuality, delayed, paused, cameraDenied, cameraMissing and cameraError in TrackingState.swift. The dashboard status strip renders their native title and detail, while DashboardWindowController refreshes the WKWebView up to five times per second when visible. Geometry is drawn only on its own tab and is cleared when its sample is more than 500 ms old. There is no exercise state today. DailyStatistics represents insufficient observations as NSNull and a measured zero as 0, so the redesign must preserve that difference.

Keep one status strip in the same place and show a plain text state, a short explanation and only the action that helps in that state. Starting and calibrating can show setup and calibration progress. Tracking and eyesClosed should have explicit text labels, since the current colored status dot cannot carry meaning by itself. For noFace, multipleFaces, lowQuality and delayed, say that current measurement is unavailable and give optional recovery guidance. Do not erase prior aggregates or convert the gap into a zero. For paused, say that camera monitoring is off and provide Resume. For cameraDenied, provide the existing camera settings action. For cameraMissing and cameraError, provide a useful retry or camera selection action and identify the device problem. These hardware states must remain distinct from a face or sample quality problem. Use a separate polite status announcement for phase changes so calibration progress and the regular dashboard refresh do not make VoiceOver repeat the same message.

Keep the screen reminder cue separate from a user started exercise session. ReminderPolicy drives a temporary screen tint and may wait for a blink to clear it. That passive cue must never start a session or count as an exercise. The header Pause currently pauses camera monitoring for five minutes, so label it Pause monitoring wherever it could be confused with Pause exercise. A single optional Exercises tab can hold session instructions without filling Activity or Geometry with another panel. Opening the tab should not start a session. Put Start in the ready state and keep Skip available without penalty.

Keep the exercise state machine independent from TrackingPhase. Ready offers Start and Skip. Running presents one clear instruction, an elapsed or remaining time value, Pause exercise and Skip. Interrupted preserves the current step and time, with Resume and Skip. Completed gives a neutral completion message and a return action. Skipped closes the session without a score or streak change. Start, Pause, Resume, Skip and timer completion should flow through the existing dashboard bridge and a separate exercise value in the native snapshot. Camera denial, missing face, multiple faces, calibration, delay, low quality and tracking loss must not interrupt, block, lower or invalidate an exercise. A user may advance, pause, finish or skip by keyboard or mouse. Do not require a blink to start, advance, complete or dismiss an exercise. Do not score exercise performance from blink counts, eyelid closure, gaze or distance. A look away prompt can be timed, but BlinkMore cannot verify what the user looked at.

Use semantic headings and native buttons in DOM order. The dashboard already implements tab roles and arrow, Home and End navigation, so extend that same pattern if Exercises becomes a fourth tab and update its selection bounds in DashboardWindowController. On entering the exercise surface, move focus to its heading or Start button. Escape during a run should change it to Interrupted and leave a clear Resume or Skip action in reach. Return or Space should activate the focused button. After leaving a session, restore focus to the control that opened it. Give the timer a readable name and value but keep frequent timer ticks out of aria-live. Announce only meaningful transitions such as started, paused, resumed, completed and skipped. The tracking status can remain readable in the page without announcing every five times per second refresh.

Respect both the current native reduced motion signal and the CSS prefers-reduced-motion setting. dashboard.css already disables CSS animation and transitions for reduced motion, but OverlayFade still animates its native window. New exercise visuals should be static when reduced motion is enabled, with text and controls carrying the same progress. Do not add looping scan lines, rotating prompts, pulsing eyes or automatic gaze movement. When reduced motion applies, make the existing screen fade immediate as well. Encode status with its words and stable icon or shape as well as color. Keep ring labels and numbers available in text. Test normal text at 4.5:1 contrast and large text, focus outlines and essential graphic boundaries at 3:1 in both themes and in the system higher contrast setting. The existing dashboard test checks only selected text colors in Geometry, so broaden the contrast check to every state and exercise action.

Acceptance in the existing macOS test harness should extend Tests/DashboardTests.swift, which already creates DashboardWindowController with a real WKWebView, injects snapshot state and instantiates MenuBarController. Inject every TrackingPhase, including starting, and assert the visible state text, optional detail, relevant action visibility and removal of stale Geometry landmarks. Inject insufficient data and measured zero separately. Verify camera states do not change a running exercise. Drive ready to running, running to interrupted and back to running, running to completed with a deterministic timer value, and ready or running to skipped. Assert that no action depends on blink events and that a skipped or camera limited session changes no score, streak or activity value. Exercise each flow with the keyboard and assert focus stays on a visible control.

Run those same WKWebView assertions in light and dark appearance, with reduced motion on and off, and with higher contrast enabled. Check contrast for the tracking strip, every action, the exercise text, the timer and keyboard focus. A VoiceOver pass in the packaged BlinkMore app should navigate all tabs, hear each tracking state once, start and pause an exercise, resume and skip it, and confirm that timer ticks do not interrupt speech. VoiceOver should also reach the native menu and hear its state and action names.

Preserve the original menu bar eye assets and native menu actions. MenuBarController currently uses OpenEye.png and ClosedEye.png for open and closed tracking and retains the native open, pause, reminders, preview, recalibrate and settings commands. The integration test should assert those images still switch only with their current tracking behavior, check the action labels and destinations, and leave the menu usable through VoiceOver. The exercise surface should not repurpose the eye icon or remove the existing menu.
